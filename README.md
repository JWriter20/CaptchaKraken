# 🐙 CaptchaKraken

**A self-hosted, AI-vision captcha solver for browser automation.** Point it at a
page, and it detects the captcha, solves the image grid with a fine-tuned
**Qwen3.5-9B** vision LoRA, and clicks through to a token — all running on *your*
hardware, no third-party solving API in the loop.

> ⭐ If this is useful, please star the repo — it genuinely helps.

---

> ### ⚠️ v2 is a breaking change
> v2 is a **ground-up rewrite**. The old approach (SAM3 grounding + general
> multi-provider LLMs like Gemini/OpenRouter/Ollama) is gone. v2 runs a single
> purpose-built grid LoRA on a local **vLLM** server and is far more robust on
> reCAPTCHA and hCaptcha image grids. If you were on v1, see
> [Migrating from v1](#migrating-from-v1) — the solver API and configuration
> changed.

## What it can solve today

CaptchaKraken v2 focuses on **image-grid** captchas — the "select all squares
with…" challenges that dominate real-world reCAPTCHA and hCaptcha. These are
fully supported end-to-end (detect → solve → click → verify):

| Captcha type | Status |
|---|---|
| ✅ Checkbox / "I'm not a robot" | Solved end-to-end (~100%) |
| ✅ **reCAPTCHA 3×3** (dynamic refresh) | Solved end-to-end (live: 48%, see below) |
| ✅ **reCAPTCHA 4×4** (one-shot) | Supported; model accuracy 76.2% |
| ✅ **hCaptcha 3×3 property grid** | Supported; model accuracy 86.7% |
| ✅ Cloudflare Turnstile (managed) | Solved via checkbox flow |

### Success rates

Two complementary numbers, because they measure different things:

**1. Model grid accuracy** — how often the LoRA picks the *exact correct tile
set* on our held-out, hand-labeled real corpus (75 samples, corrected eval
harness; the deployed `JobHarvest/qwen3.5-9b-grid-lora` adapter):

| Grid type | Exact-tile accuracy |
|---|---|
| reCAPTCHA 3×3 | **94.7%** |
| hCaptcha 3×3 property | **86.7%** |
| reCAPTCHA 4×4 | **76.2%** |
| **Overall** | **85.8%** |

**2. End-to-end browser solve rate** — full live solves against the official
demo pages through a real (Camoufox/Patchright) browser, including detection,
multi-round clicking, fades, and verification.

<!-- BEGIN E2E TABLE (generated by tests/record_demos.spec.ts) -->
| Flow | Live solve rate (preliminary) | Notes |
|---|---|---|
| reCAPTCHA 3×3 (dynamic) | ~**48%**¹ | Median solve ~20 s. Dynamic refresh means every round must be right — one missed tile across the loop fails the whole attempt. |
| reCAPTCHA 4×4 (one-shot) | model accuracy **76.2%** | One-shot "select all", no retry. A retry/verify loop to lift the end-to-end rate is on the [roadmap](#roadmap). |
| hCaptcha 3×3 property | model accuracy **86.7%** | The public hCaptcha demo only serves non-grid puzzles (drag / path / "choose the card"), so no live property-grid sample is available to record yet. |
<!-- END E2E TABLE -->

> ¹ **These live rates are preliminary and understate real performance.** Running
> many solves back-to-back from a single IP spikes Google's risk score, after
> which reCAPTCHA stops accepting *even correct* answers (verified manually: right
> tiles, still rejected). So the measured runs include attempts no solution could
> have passed — the true rate is higher. We'll re-measure under realistic
> conditions (clean / rotating IPs, human-like pacing) and update these. The
> per-grid **model accuracy** above is unaffected by IP reputation and is the
> better signal for now.

> Reproduce the live numbers yourself: `source captchakraken.env` then
> `SAMPLE_N=25 npx playwright test tests/record_demos.spec.ts`.

## Self-hosting (the only option today)

> 💡 **No GPU?** A **hosted cloud API** (solve over HTTP, no model to run) is
> coming. Star/watch the repo to be notified. For now CaptchaKraken is
> **self-hosted only** and needs a capable GPU or Apple-silicon machine.

### One-command install

```bash
bash install.sh
```

`install.sh` will:

1. **Detect your accelerator memory** (NVIDIA VRAM or Apple-silicon unified
   memory) and pick the right model quantization:

   | Detected memory | Model | Notes |
   |---|---|---|
   | **≥ 22 GB** | `RedHatAI/Qwen3.5-9B-FP8-dynamic` (8-bit) | Best accuracy — matches our config |
   | **11–22 GB** | `cyankiwi/Qwen3.5-9B-AWQ-4bit` (4-bit) | Lighter; ~5pp lower accuracy |
   | **< 11 GB** | ⛔ gated | Can't serve with headroom — see below |

2. **Download** the chosen base model + the grid LoRA
   (`JobHarvest/qwen3.5-9b-grid-lora`) from HuggingFace.

3. **Write `captchakraken.env`** with the two variables the solver needs.

**If your hardware is too small,** the installer stops and offers two choices:

- **Download anyway** (`bash install.sh --download-only`) — useful when staging
  on a dev box to copy onto a bigger server.
- **Get notified** when smaller models + the cloud API ship — link straight to
  the repo so you can watch/star.

Force a quant if you know what you want: `bash install.sh --quant fp8|awq`.

### Start the server

`install.sh` prints the exact `vllm serve …` command for your chosen model. The
critical flag is `--enable-tower-connector-lora` — without it the **vision** LoRA
is silently dropped and accuracy collapses.

```bash
source captchakraken.env
export VLLM_API_KEY="$CAPTCHA_KRAKEN_API_KEY"   # server bearer == solver key
vllm serve "RedHatAI/Qwen3.5-9B-FP8-dynamic" \
  --reasoning-parser qwen3 \
  --enable-lora --enable-tower-connector-lora \
  --max-lora-rank 64 --max-model-len 65536 \
  --gpu-memory-utilization 0.80 --trust-remote-code \
  --port 8000 \
  --lora-modules captcha-grid=JobHarvest/qwen3.5-9b-grid-lora
```

### Configuration

The solver only needs **two** environment variables (both written by
`install.sh` into `captchakraken.env`):

| Variable | Meaning |
|---|---|
| `VLLM_BASE_URL` | Inference endpoint — your local vLLM server, or the hosted cloud endpoint when it launches. |
| `CAPTCHA_KRAKEN_API_KEY` | Bearer token — your server's key today, your account key on the cloud API later. |

## Usage

```bash
npm install playwright-captcha-kraken-js
```

If you're cloning this repo, initialize the submodule that holds the
detection/planner CLI:

```bash
git submodule update --init --recursive
npm install        # builds the solver + a local CLI venv (postinstall)
```

```typescript
import { Camoufox } from '@jobharvest/camoufox-js';
import { CaptchaKrakenSolver } from 'playwright-captcha-kraken-js';

const browser = await Camoufox({ headless: false });
const page = await (await browser.newContext()).newPage();
await page.goto('https://www.google.com/recaptcha/api2/demo');

// Reads VLLM_BASE_URL + CAPTCHA_KRAKEN_API_KEY from the environment.
const solver = new CaptchaKrakenSolver();
await solver.solve(page);   // detect → solve grid → click → verify

await browser.close();
```

That's it — no model name to pass, no provider to choose. The solver defaults to
the published grid LoRA and the endpoint from your env.

## How it works

```
browser ─▶ detect captcha ─▶ screenshot frame
                                   │
                    OpenCV find_grid (color-agnostic line tracer)
                                   │  tile boxes
                                   ▼
                    Qwen3.5-9B grid LoRA on vLLM  ─▶  tile selection
                                   │
                    click plan ─▶ execute (human-like) ─▶ re-detect / verify
```

- **`find_grid`** (pure OpenCV, no model) locates the 3×3 / 4×4 lattice by
  tracing consistent-colour separator lines. It's the foundation of every solve
  and the thing CI guards most tightly. It lives in the
  [`CaptchaKraken-cli`](CaptchaKraken-cli/) submodule.
- The **grid LoRA** runs on a local vLLM server and returns the tiles to click as
  bounding boxes / ids.
- The TypeScript **solver** (this repo) drives the browser, handles reCAPTCHA's
  dynamic in-place refresh (multi-round) and 4×4 one-shot grids, and re-checks
  for follow-on challenges until solved.

## Migrating from v1

- The `apiProvider` / `model` / `apiKey` options for Gemini/OpenRouter/Ollama are
  **removed**. v2 talks only to a vLLM server.
- Set **`VLLM_BASE_URL`** and **`CAPTCHA_KRAKEN_API_KEY`** (or run `install.sh`)
  instead of provider API keys.
- `new CaptchaKrakenSolver()` now needs no model/provider — it defaults to the
  grid LoRA.
- v1's `transformers` / `torch` / SAM3 dependencies are gone from the solver venv;
  they live on the `v1-old-architecture` branch if you need them.
